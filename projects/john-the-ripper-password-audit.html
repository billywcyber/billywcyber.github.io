Overview

Purpose and scope

I used John the Ripper Jumbo to examine how different password-auditing strategies behave against a password-protected ZIP archive. The goal was to understand the workflow, interpret the output and refine an attack based on evidence—not to claim a successful recovery where none occurred.

The lab progressed from a small targeted wordlist to mangling rules, hybrid masks and finally incremental mode. Several failed commands became useful troubleshooting points and helped clarify how John handles rules and the ?w wordlist placeholder.

Portfolio-safe data

Original filenames and password information have been replaced. The fictional example password used in this write-up is Reward07!; it is not a real credential and was not recovered during the original session.

Attack sequence

What I tried and what happened

01
Basic dictionary attack — no match 
.\john.exe --wordlist=jtr-demo-wordlist.txt jtr-demo.hash

John processed every word and completed normally, but no password was recovered. This confirmed that a base word alone was insufficient.

02
Custom rules name — configuration error 
.\john.exe --wordlist=jtr-demo-wordlist.txt --rules=wordlist_rules jtr-demo.hash

John returned No "wordlist_rules" mode rules found. I had referenced a ruleset that did not exist in the installed configuration.

03
Built-in Wordlist rules — executed, no match 
.\john.exe --wordlist=jtr-demo-wordlist.txt --rules=Wordlist jtr-demo.hash

The corrected command loaded 57 preprocessed word-mangling rules and generated case, number and symbol variations. It completed without recovering the password.

04
Initial hybrid mask — syntax error

My first wordlist-and-mask command described extra characters but did not specify where John should insert the current dictionary word. The mask was rejected.

05
Corrected ?w hybrid — executed, no match 
.\john.exe --wordlist=jtr-demo-wordlist.txt --mask="?w?l?l?d?d?s" jtr-demo.hash

Using ?w fixed the syntax. The mask tested a dictionary word followed by two lowercase letters, two digits and a symbol, but that structure did not match the password.

06
Word plus symbol — executed, no match 
.\john.exe --wordlist=jtr-demo-wordlist.txt --mask="?w?s" jtr-demo.hash

This narrower test checked whether the password was simply a dictionary word followed by one symbol. The session completed without a recovery.

07
Incremental mode — stopped without recovery 
.\john.exe --incremental jtr-demo.hash

John generated progressively larger combinations independently of the custom wordlist. Despite the higher candidate rate, the password remained unrecovered during the test period.

Performance analysis

Fast guessing did not mean fast recovery

~710,000 candidates/sObserved earlier in the incremental run
~7.2 million candidates/sObserved later across 16 CPU threads

Incremental mode reached millions of candidates per second, yet the possible search space still grew too quickly. Password length, character variety and structure matter more than the speed figure alone.

For the fictional example Reward07!, a focused structure such as ?w?d?d?s represents [word][two digits][symbol]. That would be a more meaningful next refinement than continuing a blind search. I documented it as a proposed next test rather than presenting it as an attack that was run.

Final outcome

The password was not recovered. The value of the lab was the method: narrowing hypotheses, correcting configuration mistakes and recognising when a search strategy was becoming impractical.

Lessons learned

Security and analyst takeaways

•

Attack the extracted hash. zip2john converts the protected archive into a format John can process.

•

Start with realistic candidates. A targeted wordlist is far more efficient than immediately searching every possible combination.

•

Rules need valid configuration names. Built-in and custom rules must exist in John's configuration before they can be used.

•

Hybrid masks need ?w. The placeholder tells John where to insert each word from the supplied dictionary.

•

Candidate quality beats raw speed. Millions of guesses per second can still be ineffective when the assumed password structure is wrong.

•

Unsuccessful attempts are evidence. Each result eliminated a hypothesis and informed the next step.

Defensive perspective

Predictable monthly changes such as a repeated base word plus an incrementing number remain vulnerable even when the password technically changes. Stronger protection comes from long unique passwords, password managers, multi-factor authentication, and controls that detect or limit repeated authentication attempts.

Ethical use

Authorised testing only

This exercise was documented as a controlled cybersecurity learning activity using a test archive. Password-auditing tools should only be used on files, hashes, accounts or systems that you own or have explicit permission to assess.
