Scenario and scope

What I was investigating

In KC7's fictional OWL Records scenario, a public feud between artists Dwake and Present creates a possible security exposure. Acting as an OWL Records security analyst, I examined whether someone used public information about Dwake to target his account.

Work in progress

This case study covers the opening investigation through the security-question request. Later questions, outcomes and any final incident timeline will be added after I complete the exercise.

Initial lead

Establish the organisation and narrow the web activity

I first used the Employees table to locate the CEO record, then investigated the supplied source IP in InboundNetworkEvents. The employee lookup established the organisation's dataset and introduced fields such as usernames and email addresses; it did not identify the web visitor.

Employees
| where role == "CEO"

The query returned Sean Crater as CEO. For the network lead, I applied the exercise's time window and source IP:

InboundNetworkEvents
| where timestamp between (datetime("2024-04-10T00:00:00") .. datetime("2024-04-11T00:00:00"))
| where src_ip == "18.66.52.227"

This yielded 19 web events. I reviewed the timestamps, requested URLs and status codes to understand what the visitor sought. The IP is a scenario indicator, not proof of a person's identity.

Evidence pivots

Contact searches led to an account recovery route

01
Search intent

Requested URLs repeatedly searched for Dwake's email address, contact details and booking information. This pattern pointed to targeted information gathering.

02
Account identifier

The activity exposed dwake_audrey@owl-records.com and showed a password reset request associated with username dwaubrey.

03
Recovery questions

Subsequent requests referenced a mother's maiden name and a first pet. The investigation then compared those prompts with details disclosed in Dwake's verse.

Account recovery activity

Correlating public clues with the submitted answers

The verse disclosed the values Washington and Fluffy. A web event from 18.66.52.227 at 2024-04-10 13:02:47 UTC contained those values in a request to the OWL Records security-question endpoint. This ties the public clues to a concrete recovery request.

InboundNetworkEvents
| where src_ip == "18.66.52.227"
| where url has "Washington" and url has "Fluffy"
| project timestamp, method, src_ip, url, status_code

The query above is a compact reconstruction of the filtering approach for this write-up; the KC7 exercise supplied some of the tutorial queries. The logged request used the two answers as URL parameters and returned HTTP 200. That response shows the endpoint handled the request; by itself it does not establish that the answers were accepted or the password was changed.

Analyst assessment

What the current evidence supports

•

The source IP conducted focused searches for Dwake's contact information, followed by password recovery and security-question activity.

•

The recovery request contained the same answers revealed publicly in the verse. This is evidence of an account takeover attempt, with the final outcome still under investigation.

•

Putting recovery answers in GET URL parameters can expose them in logs and browser history. The scenario illustrates why publicly discoverable facts make weak recovery factors.

Next investigative step: check subsequent authentication, reset and account activity before concluding whether the account was compromised. I will extend this page as the rest of the KC7 investigation is completed.
